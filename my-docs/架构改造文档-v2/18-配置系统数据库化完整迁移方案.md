### 1.2 Gateway 当前启动流程

```
server.impl.ts:212  →  const cfgAtStart = loadConfig()    ← 从 mtbot.json 加载
                             │
                             ▼

                             ▼
```

- `loadConfig()` 返回完整的 `MtBotConfig` 类型
- `cfgAtStart` 被传递到 40+ 个子系统

## 2. 迁移目标与原则

### 2.1 核心目标

1. **数据库作为多租户场景的配置权威源** — 每个用户可拥有私有配置
2. **文件配置保持向后兼容** — 个人部署/开发场景仍可用 `mtbot.json`
3. **保证网关正常运行** — 不破坏现有 Gateway 启动流程和 Agent 会话
4. **支持私有配置** — 租户级覆盖系统配置的特定段

### 2.2 配置优先级（从高到低）

```
租户数据库配置 → 系统数据库配置 → 文件配置 → 环境变量 → 代码默认值
```

### 2.3 设计原则

1. **渐进式迁移** — 分阶段实施，每个阶段独立可用
2. **数据库失败不阻塞启动** — 数据库不可用时 fallback 到文件配置
3. **字段级深度合并** — 不是简单的整段替换，而是精确到字段的 deepMerge
4. **最小改动原则** — 不改动 `MtBotConfig` 类型定义，仅在加载层注入数据库值
5. **租户可覆盖范围受限** — 基础设施字段 (port/bind/tls) 不允许租户覆盖

## 4. 新增数据库表设计

### 4.1 `auth_profiles` 表（新建）

存储 AI 提供商认证配置，替代文件中的 `auth.profiles` + `auth.order` + `auth.cooldowns`。

```sql
CREATE TABLE auth_profiles (
  id TEXT PRIMARY KEY,

  -- 多租户: system / tenant
  config_type VARCHAR(20) NOT NULL DEFAULT 'system',
  user_id TEXT REFERENCES users(id) ON DELETE CASCADE,

  -- Profile 标识
  profile_id VARCHAR(100) NOT NULL,  -- 对应 auth.profiles 的 key，如 "anthropic-main"

  -- 认证信息
  provider VARCHAR(100) NOT NULL,     -- "anthropic", "openai", "google" 等
  mode VARCHAR(20) NOT NULL,          -- "api_key" | "oauth" | "token"
  email VARCHAR(255),                 -- OAuth 关联邮箱（可选）
  api_key TEXT,                       -- API Key (加密存储)

  -- 优先级配置
  priority INTEGER DEFAULT 100,       -- 同一 provider 内的优先级
  enabled BOOLEAN DEFAULT TRUE,

  -- Cooldown 配置
  cooldowns JSONB,                    -- {billingBackoffHours, billingMaxHours, failureWindowHours}

  -- 模型→Profile 映射 (对应 auth.order)
  model_bindings JSONB,               -- {"claude-opus-4-5": true, "gpt-4": true} 或 null=全局

  -- 元数据
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  created_by TEXT,
  updated_by TEXT,

  -- 约束: 同一 (configType, userId, profileId) 唯一
  CONSTRAINT auth_profiles_unique UNIQUE (config_type, user_id, profile_id)
);

CREATE INDEX auth_profiles_user_idx ON auth_profiles(user_id);
CREATE INDEX auth_profiles_provider_idx ON auth_profiles(provider);
```

## 5. 实施方案（分 3 个 Phase）

### Phase 1: 接入核心 — 数据库配置合并到 Gateway 启动

**目标**: 让已有的数据库配置表真正生效，Gateway 能从数据库加载配置。

**改动清单**:

#### 5.1.1 新增 `src/gateway/config-merger.ts` — 配置合并器

核心函数，将文件配置与数据库配置合并为最终的 `MtBotConfig`。

```typescript
/**
 * 配置合并器
 *
 * 将数据库配置覆盖到文件配置上，生成最终的 MtBotConfig。
 * 原则: 数据库有值则覆盖文件对应字段，数据库无值则保留文件值。
 */

import type { MtBotConfig } from "../config/types.js";
import type { GatewayConfig as DbGatewayConfig } from "../db/schema/gateway-configs.js";
import type { ModelProvider } from "../db/schema/model-configs.js";
import type { AgentDefaultConfig } from "../db/schema/model-configs.js";

interface DatabaseConfigs {
  gatewayConfig: DbGatewayConfig | null;
  modelProviders: ModelProvider[];
  agentConfig: AgentDefaultConfig | null;
  systemConfigs: Record<string, unknown>; // system_configs 键值对
}

/**
 * 合并文件配置和数据库配置
 *
 * @param fileConfig - 从 mtbot.json 加载的配置
 * @param dbConfigs  - 从数据库加载的配置集合
 * @returns 合并后的 MtBotConfig
 */
export function mergeFileAndDbConfigs(
  fileConfig: MtBotConfig,
  dbConfigs: DatabaseConfigs,
): MtBotConfig {
  let merged = { ...fileConfig };

  // 1. 合并 gateway 配置
  if (dbConfigs.gatewayConfig) {
    merged = mergeGatewayConfig(merged, dbConfigs.gatewayConfig);
  }

  // 2. 合并 model providers
  if (dbConfigs.modelProviders.length > 0) {
    merged = mergeModelProviders(merged, dbConfigs.modelProviders);
  }

  // 3. 合并 agent 默认配置
  if (dbConfigs.agentConfig) {
    merged = mergeAgentConfig(merged, dbConfigs.agentConfig);
  }

  // 4. 合并 system_configs 键值对 (B类配置)
  merged = mergeSystemConfigs(merged, dbConfigs.systemConfigs);

  return merged;
}
```

**合并规则**:

| 字段来源                               | 合并策略                                                    |
| -------------------------------------- | ----------------------------------------------------------- |
| `gateway.port` / `gateway.bind` 等标量 | 数据库非 null 则覆盖                                        |
| `gateway.extraConfig` JSONB            | deepMerge 到 `gateway.tls/http/nodes/reload` 等             |
| `model_providers` 列表                 | 按 `providerKey` 合并：数据库存在则替换，不存在则保留文件的 |
| `agent_configs`                        | 数据库非 null 字段覆盖文件中的 agents defaults              |
| `system_configs` 键值                  | 按 key 写入对应配置段                                       |

#### 5.1.2 修改 `src/gateway/config-loader.ts` — 扩展为完整配置加载入口

```typescript
/**
 * 从数据库加载所有配置表的数据
 *
 * @returns DatabaseConfigs 或 null (数据库不可用时)
 */
export async function loadAllDatabaseConfigs(userId?: string): Promise<DatabaseConfigs | null> {
  try {
    const db = getDatabase();

    const [gatewayConfig, modelProviders, agentConfig] = await Promise.all([
      new GatewayConfigRepository(db).getEffectiveConfig(userId),
      new ModelProviderRepository(db).listEffectiveProviders(userId),
      new AgentDefaultConfigRepository(db).getEffectiveConfig(userId),
    ]);

    // 加载 system_configs 中的 B 类配置
    const systemConfigs = await loadSystemConfigEntries([
      "logging",
      "session",
      "messages",
      "cron",
      "hooks",
      "approvals",
      "talk",
      "ui",
      "tools",
    ]);

    return { gatewayConfig, modelProviders, agentConfig, systemConfigs };
  } catch (error) {
    logger.warn("[ConfigLoader] 数据库配置加载失败，将使用文件配置:", error);
    return null;
  }
}
```

#### 5.1.3 修改 `src/gateway/server.impl.ts` — 注入数据库配置

```typescript
// 现有代码 (line 212):
const cfgAtStart = loadConfig();

// 改为:
const fileConfig = loadConfig();
const dbConfigs = await loadAllDatabaseConfigs();
const cfgAtStart = dbConfigs ? mergeFileAndDbConfigs(fileConfig, dbConfigs) : fileConfig;
```

**关键约束**:

- `server.impl.ts` 仅改动配置加载部分（约 5 行）
- `cfgAtStart` 的类型仍然是 `MtBotConfig`，下游代码无需任何改动
- 数据库加载失败时，完全回退到文件配置，Gateway 正常启动

#### 5.1.4 测试验证

```
场景 1: 数据库无配置 → 纯文件配置启动 → Gateway 正常运行
场景 2: 数据库有系统配置 → 数据库覆盖文件配置 → 验证覆盖生效
场景 3: 数据库不可用 → fallback 到文件配置 → Gateway 正常运行
场景 4: 启动后通过 config.get RPC 检查配置值来源
```

### Phase 3: 配置热更新 — 数据库变更实时生效

**目标**: 数据库配置变更后，Gateway 能自动感知并应用，无需重启。

#### 5.3.1 变更通知机制

**方案选择**: PostgreSQL LISTEN/NOTIFY

```sql
-- 创建通知触发器
CREATE OR REPLACE FUNCTION notify_config_change() RETURNS trigger AS $$
BEGIN
  PERFORM pg_notify(
    'config_changed',
    json_build_object(
      'table', TG_TABLE_NAME,
      'operation', TG_OP,
      'id', COALESCE(NEW.id, OLD.id),
      'user_id', COALESCE(NEW.user_id, OLD.user_id)
    )::text
  );
  RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

-- 绑定到配置表
CREATE TRIGGER gateway_configs_notify
  AFTER INSERT OR UPDATE OR DELETE ON gateway_configs
  FOR EACH ROW EXECUTE FUNCTION notify_config_change();

CREATE TRIGGER model_providers_notify
  AFTER INSERT OR UPDATE OR DELETE ON model_providers
  FOR EACH ROW EXECUTE FUNCTION notify_config_change();

CREATE TRIGGER agent_configs_notify
  AFTER INSERT OR UPDATE OR DELETE ON agent_configs
  FOR EACH ROW EXECUTE FUNCTION notify_config_change();

CREATE TRIGGER auth_profiles_notify
  AFTER INSERT OR UPDATE OR DELETE ON auth_profiles
  FOR EACH ROW EXECUTE FUNCTION notify_config_change();
```

## 7. 风险与缓解

| 风险                            | 影响 | 缓解措施                                                         |
| ------------------------------- | ---- | ---------------------------------------------------------------- |
| 数据库不可用时 Gateway 无法启动 | 高   | Phase 1 确保: `dbConfigs ? merge : fileConfig`，数据库失败不阻塞 |
| 配置合并逻辑复杂导致行为不一致  | 中   | 详细日志标注每个字段的来源 (file/db-system/db-tenant)            |
| 热重载导致正在进行的会话中断    | 中   | 会话级别配置在会话创建时快照，不受后续变更影响                   |
| 租户覆盖导致安全问题            | 中   | 白名单限制可覆盖字段，基础设施字段仅管理员可改                   |
| LISTEN/NOTIFY 连接断开          | 低   | 自动重连 + 重连后全量加载一次                                    |
| 文件配置和数据库配置冲突        | 中   | 明确优先级文档，提供 `config.get` RPC 查看有效配置来源           |

## 9. 与现有配置 RPC 的关系

Gateway 已有 `config.get` / `config.set` / `config.patch` / `config.schema` RPC 方法 (在 `src/gateway/server-methods/config.ts`)。

**Phase 1 阶段**: 这些 RPC 继续操作文件配置（`mtbot.json`），不受影响。

**Phase 2 阶段**: 考虑扩展:

- `config.get` 返回合并后的有效配置（标注来源）
- `config.set` / `config.patch` 写入数据库（非文件），成为数据库配置的管理入口
- 新增 `config.sources` RPC 方法，返回每个字段的来源信息

**Phase 3 阶段**: `config.set` 触发数据库写入 → PG NOTIFY → 热重载。
