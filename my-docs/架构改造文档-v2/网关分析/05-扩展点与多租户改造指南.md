# 多用户多设备架构改造指南

> 文档版本：v4.0 | 更新日期：2026-02-22
>
> **核心定位**：用户级隔离，每个用户拥有私有化助理、多设备控制、多通道接入。
> **设计原则**：不过度设计；不向后兼容单用户遗留模式；隔离数据全部走数据库；暴露真实问题。
> **客户端范围**：仅 Windows 客户端。
> **管理端定位**：Admin Console 纯系统管理，不涉及用户私人配置。

---

## 1. 改造目标

```
┌──────────────────────────────────────────────────────────────────┐
│                        目标场景                                    │
│                                                                    │
│  用户 A ──┬─ Windows App (电脑1)  ──┐                              │
│           ├─ Windows App (电脑2)     ├─▶ Gateway → 用户 A 的 Agent │
│           └─ Telegram / 微信         ┘   (独立配置/记忆/会话)       │
│                                                                    │
│  用户 B ──┬─ Windows App ────────────┐                              │
│           └─ Discord                  ├─▶ Gateway → 用户 B 的 Agent │
│                                      ┘                             │
│  Admin ────── Admin Console ──────────▶ 系统管理/监控/日志          │
└──────────────────────────────────────────────────────────────────┘
```

**核心需求**：

| 需求       | 说明                                                     |
| ---------- | -------------------------------------------------------- |
| 用户隔离   | 每个用户独立的助理配置、对话记忆、会话历史、Auth Profile |
| 多设备     | 同一用户多台 Windows 设备 + 消息频道，设备间会话实时同步 |
| 设备管理   | 用户在客户端注册/绑定/解绑/控制设备，设备有独立权限      |
| 自定义助理 | 用户在客户端配置助理角色、行为模式、系统提示词、模型偏好 |
| 多通道接入 | 用户可通过 Telegram/微信/Discord 等消息频道发消息给助理  |
| 数据库存储 | 所有隔离数据使用 DB 存储，移除文件系统遗留方案           |
| 无人值守   | 设备可长期无人值守运行，不因 token 过期断连              |

## 3. 设备认证方案

### 3.1 认证模型设计

核心问题：用户 JWT 有时效限制，但设备需要无人值守长期在线。

**方案：双层认证，设备绑定后以 Device Token 为主**

```
┌─────────────────────────────────────────────────────────────┐
│                    认证分层模型                                │
│                                                               │
│  第一层: 用户认证 (交互式，仅在绑定/登录时使用)                  │
│    ├─ JWT accessToken (15分钟) + refreshToken (30天)           │
│    ├─ 用途: 用户注册/登录、设备首次绑定、API Server REST 接口    │
│    └─ 场景: 用户主动操作                                       │
│                                                               │
│  第二层: 设备认证 (无人值守，长期有效)                           │
│    ├─ Device Token (32字符随机令牌，无过期时间)                  │
│    ├─ 用途: WebSocket 网关连接                                  │
│    ├─ 特性: 支持轮换 (rotate) 和撤销 (revoke)                   │
│    └─ 场景: 设备启动后自动连接网关，长期保持连接                  │
│                                                               │
│  绑定关系: Device Token 颁发时与 userId 绑定                    │
│            网关通过 deviceId 反查 userId                         │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 设备生命周期

```
1. 用户登录 (JWT)
   用户在 Windows 客户端输入账号密码
   → API Server 返回 accessToken + refreshToken
   → 客户端保存到本地

2. 设备绑定 (JWT → Device Token)
   客户端生成 deviceId (UUID) + Ed25519 密钥对
   → 调用 REST API: POST /api/devices/bind (携带 accessToken)
   → 服务端验证 JWT，检查设备配额
   → 创建 device 记录，userId 关联，生成 Device Token
   → 返回 Device Token 给客户端持久化存储

3. 网关连接 (Device Token，无需 JWT)
   客户端启动 → 读取本地 Device Token
   → WebSocket connect 帧携带 { auth: { deviceId, token } }
   → 网关验证 Device Token → 查 DB 获取 userId
   → 填充 client.authenticatedUser
   → 连接成功，设备上线

4. 无人值守运行
   设备保持 WebSocket 长连接
   → 断线自动重连 (仍用 Device Token)
   → 无需 JWT 参与，不存在过期问题

5. 安全轮换 (定期)
   客户端定期调用 device.token.rotate RPC
   → 服务端生成新 Token，标记旧 Token 的 rotatedAtMs
   → 客户端更新本地存储的 Token

6. 设备撤销
   用户在客户端或管理员在 Admin Console 撤销设备
   → 设备 Token 标记 revokedAtMs
   → 网关强制断开该设备连接
```

### 3.3 网关认证改造

**改造文件**：`src/gateway/auth.ts`

```typescript
/**
 * 网关连接认证流程：
 * 1. 验证 Device Token
 * 2. 通过 deviceId 查 DB 获取 userId
 * 3. 检查设备和用户是否都处于活跃状态
 */
async function authorizeGatewayConnect(params: ConnectParams): Promise<GatewayAuthResult> {
  const { deviceId, token } = params.auth ?? {};
  if (!deviceId || !token) {
    return { ok: false, reason: "device-auth-required" };
  }

  // 步骤 1: 验证 Device Token
  const device = await verifyDeviceToken(deviceId, token);
  if (!device) {
    return { ok: false, reason: "invalid-device-token" };
  }

  // 步骤 2: 检查设备已绑定用户
  if (!device.userId) {
    return { ok: false, reason: "device-not-bound" };
  }

  // 步骤 3: 检查用户活跃状态
  const user = await loadUser(device.userId);
  if (!user || !user.isActive) {
    return { ok: false, reason: "user-inactive" };
  }

  return {
    ok: true,
    method: "device-token",
    userId: device.userId,
    deviceId: device.deviceId,
  };
}
```

### 3.4 安全防线

| 威胁              | 防御措施                                           |
| ----------------- | -------------------------------------------------- |
| Device Token 泄露 | 管理员或用户随时撤销，定期轮换                     |
| 设备丢失          | 用户在另一设备解绑该设备，Token 立即失效           |
| 用户账号被禁      | 网关检查 user.isActive，禁用用户的所有设备自动断连 |
| 重放攻击          | Device Token 结合 deviceId 验证，单设备单 Token    |
| 暴力猜测          | 32 字符随机令牌 (62^32 ≈ 2×10^57 种组合)           |

#### 4.1.3 NodeRegistry 增加用户维度

**改造文件**：`src/gateway/node-registry.ts`

```typescript
class NodeRegistry {
  private nodesById = new Map<string, NodeSession>()
  private nodesByConn = new Map<string, string>()
  private nodesByUser = new Map<string, Set<string>>() // 新增

  register(client: GatewayWsClient): NodeSession {
    const session = /* 现有逻辑 */
    const userId = client.authenticatedUser!.userId
    const userNodes = this.nodesByUser.get(userId) ?? new Set()
    userNodes.add(session.nodeId)
    this.nodesByUser.set(userId, userNodes)
    return session
  }

  /** 获取用户的所有在线设备 */
  getNodesByUser(userId: string): NodeSession[] {
    const nodeIds = this.nodesByUser.get(userId)
    if (!nodeIds) return []
    return [...nodeIds]
      .map((id) => this.nodesById.get(id))
      .filter(Boolean) as NodeSession[]
  }
}
```

#### 4.1.4 事件广播到用户所有设备

```typescript
function emitToUser(userId: string, event: GatewayEvent): void {
  const nodes = nodeRegistry.getNodesByUser(userId);
  for (const node of nodes) {
    emitToClient(node.client, event);
  }
}
```

### 5.2 设备绑定流程

```
用户首次使用
  ├─ 打开 App → 显示登录/注册页

  ├─ 客户端生成 deviceId + Ed25519 密钥对

  ├─ 服务端: 验证 JWT → 检查设备配额 → 创建 device 记录 → 生成 Device Token

  └─ 连接网关 (使用 Device Token，不再需要 JWT)

后续启动
  ├─ 读取本地 deviceId + deviceToken
  ├─ 直接连接网关 → 无需登录页
  └─ 断线自动重连 → 同样使用 Device Token
```

## 9. 设计原则

### 9.1 不过度设计

- **不引入 tenantId**：userId 就是隔离单元
- **不引入微服务**：所有改造在现有单进程 Gateway 内完成
- **不引入新中间件**：复用现有 PostgreSQL + WebSocket
- **只做 Windows 客户端**：其他平台后续按需扩展

### 9.2 不向后兼容

- 移除 `DEFAULT_USER_ID = "default"` 回退
- 移除全局 token/password 认证
- 移除旧格式 Session Key
- 移除文件系统存储的隔离数据
- 未认证连接直接拒绝

### 9.3 安全边界

| 安全要求 | 实现方式                                       |
| -------- | ---------------------------------------------- |
| 连接认证 | Device Token 验证 → deviceId → userId          |
| 设备归属 | device.userId 外键，绑定后才颁发 Token         |
| 无人值守 | Device Token 无过期时间，支持轮换/撤销         |
| 会话隔离 | Session Key 含 userId + TenantScopedRepository |
| 配置隔离 | DB configType + userId 联合唯一约束            |
| 事件隔离 | emitToUser() 只向同用户设备广播                |
| 设备权限 | role + scopes 控制 RPC 方法访问                |
| 账号禁用 | user.isActive 检查，禁用后所有设备断连         |
