## 1. 改造目标

将记忆系统从当前的"接口已定义 + 内存提供者"状态，推进到"生产级可用"状态：

- 简化接口层：5 层 → 3 层，87 方法 → ~35 方法
- 实现 PostgreSQL Profile 提供者（连接已有 Schema 和 Repository）
- 实现 PostgreSQL Episodic 提供者（连接 user_memories 表）
- 实现 Gateway RPC 记忆方法
- 将可插拔记忆系统与 Agent 运行时集成
- 建立从旧版记忆系统到新版的迁移路径

**不在本次范围内**: Mem0 集成、Graphiti 知识图谱、MinIO 对象存储、GraphRAG（接口已预留 @future）

**目标**: 在 Agent 运行时中集成记忆系统，实现自动记忆回忆和捕获。

| 操作   | 文件                                           | 说明                     |

| 已创建 | `src/hooks/bundled/session-memory/recall.ts`   | before_agent_start: 回忆 |

| 已创建 | `src/hooks/bundled/session-memory/register.ts` | hook 注册到全局 registry |
| 修改   | `src/gateway/server.impl.ts`                   | 调用 registerMemoryHooks |

**自动回忆流程**:

```
用户发消息 → before_agent_start hook 触发
  ↓
1. 从 Profile 获取用户偏好和事实
2. 从 Episodic 搜索相关历史记忆（基于当前消息语义）
3. 组装 system prompt 上下文注入
  ↓
Agent 收到带有记忆上下文的请求
```

**自动捕获流程**:

```
Agent 响应完成 → agent_end hook 触发
  ↓
1. 分析对话内容，检测可捕获信息
2. 提取用户事实 → Profile.addFact
3. 提取关键事件 → Episodic.addKeyEvent
4. 生成对话摘要 → Episodic.addConversation
  ↓
记忆更新完成
```

**验收标准**:

- [x] Agent 启动时自动注入相关记忆上下文（recall hook: 事实 + 偏好 + 情节搜索）
- [x] Agent 完成后自动捕获对话内容（capture hook: 消息转换 + addConversation）
- [x] 用户事实通过 recall 注入 system prompt（filterFacts + formatFacts）
- [x] 对话自动保存到情节记忆（convertMessages + fire-and-forget）

## 6. 技术决策记录

### 6.1 为什么移除工作记忆层？

- Agent 运行时（pi-agent-core）已自行管理会话上下文
- 工作记忆 18 个方法中没有任何生产实现
- 会话级临时状态不需要可插拔后端

### 6.2 为什么移除对象存储层？

- 当前多媒体处理由 `src/media/` 模块独立处理
- 对象存储（MinIO/S3）属于基础设施，与记忆系统职责不同
- 后续作为独立模块实现更合适

### 6.3 为什么推迟知识图谱/GraphRAG？

- 需要额外部署 Neo4j 服务，增加运维复杂度
- 当前用户场景以个人助理为主，知识图谱需求优先级低
- 可通过 PostgreSQL JSONB + pgvector 满足基本的知识检索
- 类型定义已保留并标记 @future，需要时可快速实现

### 6.4 为什么先实现 PostgreSQL 而非 Mem0？

- PostgreSQL Schema 和 Repository 已经完整实现，可直接复用
- 不引入新的外部依赖（Mem0 需要 API Key 或自托管服务）
- PostgreSQL + pgvector 已满足基本的向量搜索需求

### 6.5 为什么保留旧版 MemoryIndexManager？

- 旧版提供的文件索引 + SQLite-vec 向量搜索 + BM25 混合搜索在新系统中没有直接替代
- SQLiteKnowledgeMemoryAdapter 已桥接新旧系统，旧版作为知识记忆后端继续工作
- 旧版仅有 4 处非测试代码直接引用（memory-tool.ts, memory-cli.ts, status.scan.ts, memory-service.ts）
- 已标记 @deprecated，后续如需全面清理可作为独立任务（需在新系统中重新实现文件索引功能）

## 7. 风险与缓解

| 风险                        | 影响       | 缓解措施                                 |
| --------------------------- | ---------- | ---------------------------------------- |
| pgvector 索引性能不足       | 搜索延迟高 | 确保 HNSW 索引已创建；监控查询延迟       |
| 旧版记忆系统与新版冲突      | 数据不一致 | 使用特性开关隔离；渐进式迁移             |
| LLM 自动摘要/提取质量低     | 记忆质量差 | 先实现简单版（关键词提取），后续接入 LLM |
| memory-lancedb 与新系统重叠 | 功能冲突   | 明确分工：lancedb 保持独立扩展角色       |
